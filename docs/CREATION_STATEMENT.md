# “诊路”微信小程序创作说明

## 一、项目名称

诊路——罕见病患者病程整理与复诊准备助手

## 二、创作背景

罕见病患者通常需要经历较长时间的检查、转诊和随访。患者及照护者手中往往积累了检查报告、就诊记录、用药信息和复诊问题，但这些资料分散在纸张、聊天记录、相册和不同设备中，临近就诊时很难快速整理。

传统的病历整理工具通常面向普通健康管理，较少关注罕见病患者长期记录、照护者协作和复诊准备等场景。与此同时，检验报告中的项目名称、结果、单位和参考区间需要反复手工录入，增加了整理成本。

因此，本项目希望设计一个轻量、克制、隐私优先的工具：帮助用户把已有资料整理成可复诊使用的材料，但不替代医生，也不对检验结果作医疗判断。

## 三、用户与场景

### 主要用户

- 需要长期随访的罕见病患者；
- 协助患者整理资料的家属和照护者；
- 需要在就诊前快速回顾病程的用户。

### 典型场景

1. 用户建立患者档案，记录病种、阶段和主要就诊科室。
2. 用户持续记录检查、就诊和用药等病程事件。
3. 用户拍摄或选择检验报告，通过 OCR 提取文字。
4. 用户人工核对 OCR 结果，并将报告保存为病程事件。
5. 用户创建复诊计划，选择需要携带的材料并整理问题清单。
6. 用户通过一次性邀请码，将最小必要内容以只读方式共享给照护者。

## 四、创作思路

### 1. 从“记录更多”转向“复诊时更有用”

项目不追求堆叠复杂健康功能，而是围绕一次真实复诊设计流程：资料在哪里、发生过什么、下次要问什么、哪些内容需要带给医生。所有功能都服务于“整理—核对—准备”这条主线。

### 2. 本地优先，主动上云

患者资料默认保存在当前设备。只有在用户明确操作时，才使用 OCR、云备份或照护共享。这样可以减少不必要的数据传输，也让用户清楚知道数据何时离开设备。

### 3. AI 辅助录入，不做医疗判断

OCR 只负责从报告图片中提取文字。识别结果必须经过人工核对后才能保存，产品不解释指标是否正常，不给出诊断、治疗或用药建议。

### 4. 共享最小化

照护者共享采用一次性邀请码和只读快照。患者称呼、检验明细等敏感字段默认关闭，管理者可以更新、取消或撤销授权，照护者不能直接修改原始档案。

### 5. 把数据权利设计成产品功能

隐私政策、用户协议、撤回同意、本地数据清除、云端数据查询和全量删除都被设计成可操作的页面，而不是只放在文档中的承诺。

## 五、实践过程

### 第一阶段：需求拆解和产品边界

首先将需求拆解为患者档案、病程时间线、复诊计划、报告识别和数据管理五条主线，同时明确不做诊断、治疗建议和公开病历分享，避免产品定位失控。

### 第二阶段：本地病程模型

使用版本化的数据模型保存患者、病程事件和复诊计划。通过统一的数据服务处理新增、编辑、删除、切换和迁移，保证早期数据能够升级到当前模型版本。

### 第三阶段：OCR 与人工核对

在设备端先压缩图片，再上传到微信云存储临时目录。云函数下载临时文件后调用百度医疗检验报告单 OCR，返回结构化结果；前端展示报告基本信息和逐项指标，用户核对后才写入病程。识别完成后删除临时图片。

### 第四阶段：云备份

云备份不允许客户端指定用户身份。云函数通过微信调用上下文获取当前微信身份，并使用不可逆摘要生成备份文档标识。客户端只发送业务数据，不发送 OpenID。

### 第五阶段：照护者协作

为避免直接共享整份病历，先根据用户选择生成最小化快照，再通过一次性、高随机度、限时邀请码建立只读授权。授权双方分别拥有取消、撤销或退出权限。

### 第六阶段：隐私和上线准备

新增版本化隐私同意、隐私政策和用户协议页面，支持用户查看和撤回同意。增加云端数据统计与全量删除，统一处理云服务错误，加入 OCR、备份和共享限流，并补充上线配置和验收文档。

## 六、技术实践

### 技术栈

- 微信原生小程序：JavaScript、WXML、WXSS、JSON；
- 微信云开发：Node.js 云函数、云数据库、云存储；
- 百度医疗检验报告单 OCR；
- Node.js `node:test` 自动化测试；
- Git 版本管理。

### 核心安全设计

- 正式 AppID 和服务密钥不进入仓库；
- OCR 密钥仅配置在云函数环境变量；
- 云函数从微信上下文确认身份；
- 业务集合和限流集合禁止客户端直接读写；
- 临时报告图片在流程结束后删除；
- 错误提示隐藏调用链、请求标识和平台内部信息；
- 示例病例禁止上传和恢复云备份；
- 用户可以分别清除本地数据和云端数据。

## 七、实践难点与解决方法

### 难点一：医疗信息的敏感性

解决方法是采用本地优先、主动上云、最小化共享和可删除设计，并在界面中明确产品不提供医疗判断。

### 难点二：OCR 结果不等于真实病历

解决方法是将 OCR 定位为辅助录入工具，强制保留人工核对步骤，并在报告页面和用户协议中提示识别可能存在错误。

### 难点三：不同微信身份的数据隔离

解决方法是所有云端操作都由服务端基于当前微信身份执行，不接受前端传入的身份参数，并通过双账号测试验证授权边界。

### 难点四：云函数错误不易定位

解决方法是统一错误分类，将函数未部署、网络失败、超时、数据库缺失、权限错误和额度不足转换成用户可理解的提示，同时保留云端日志供维护人员排查。

### 难点五：示例数据污染正式数据

解决方法是给示例患者打上 `isDemo` 标记，只要设备中存在示例病例，就禁用云备份和恢复按钮，防止演示资料上传到正式账号。

## 八、项目成果

当前版本已经实现：

- 患者档案和病程事件完整管理；
- 检验报告图片自动压缩和 OCR 识别；
- OCR 结果人工核对后保存；
- 复诊材料、问题清单和摘要整理；
- 个人云备份、恢复和删除；
- 一次性邀请码照护者只读共享；
- 隐私同意、政策查看和数据权利管理；
- 云端错误处理、限流和过期记录清理；
- 59 项自动化测试全部通过；
- 已完成开发者工具和真机基础验证。

项目代码体量约 3,600 行非空小程序代码，文档和配置完整，便于后续维护或移交公益组织。

## 九、创新与社会价值

### 1. 面向复诊准备的细分场景

项目没有试图替代医院系统，而是解决患者在两次就诊之间如何整理资料、回顾病程和准备问题这一具体问题。

### 2. 兼顾效率和谨慎性

OCR 降低录入成本，人工核对和产品边界又降低误解风险；云功能提供便利，但默认不主动上传医疗资料。

### 3. 支持患者与照护者协作

通过最小范围、只读和可撤销的设计，让照护者能够参与资料准备，同时降低过度共享风险。

### 4. 适合公益场景持续运营

项目不依赖自建服务器，部署在微信云开发上，初期运维门槛较低；代码、配置、验收和隐私文档相对完整，便于公益组织接手。

## 十、当前局限与后续计划

当前版本仍有以下限制：

- OCR 识别准确率受图片质量、版式和第三方服务影响；
- 云函数限流目前属于基础实现，高并发场景需要进一步强化原子性；
- 暂无专业运营后台和人工客服系统；
- 隐私政策需要根据最终运营主体和实际地区进行专业复核；
- 微信云开发和百度 OCR 存在第三方服务依赖。

后续计划包括：

1. 完成正式 AppID、云环境和费用监控配置；
2. 通过小规模试用收集脱敏反馈；
3. 优化 OCR 字段核对和异常提示；
4. 完善数据导出、迁移和灾难恢复；
5. 与罕见病公益组织讨论长期运营和公益授权。

## 十一、结语

“诊路”的创作重点不是让技术替代医生，而是让患者和照护者在面对长期、复杂、分散的病程资料时，拥有一个更清晰、更可控的整理工具。

项目将隐私、人工核对和医疗边界放在功能效率之前，希望通过可靠的基础工具，减少复诊准备中的重复劳动，把更多时间留给患者、照护者与医疗专业人员之间的沟通。
